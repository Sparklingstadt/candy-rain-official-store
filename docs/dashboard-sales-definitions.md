# 管理ダッシュボードの金額指標

2026-10-26。PR #105 の注文総額を「売上」と表示する仕様を見直す。

## 採用した表示

- **注文総額**：注文日時が期間内で、発送状態がキャンセル以外の `totalPrice` の合計。未決済も含む受注規模を表す。従来の集計値を維持する。
- **決済済み売上**：同じ注文のうち `paymentStatus = 支払い済み` の合計。件数も支払い済みだけを数える。決済成功が記録された有効な注文の現在額であり、銀行への入金額や会計上の収益を示さない。
- **返金を考慮した入金額**：本来は成功した売上確定額から成功した実返金額を控除する指標。返金失敗は控除せず、キャンセルだけでも入金を消さない。現行データでは正確に算出できないため、数値表示しない。

いずれの表示額も送料込み。日本時間の当日・当月の開始を `tokyoPeriodStarts` で求め、従来どおり `orderedAt >= since` を対象とする。日次・月次は**注文日の集団を現在の状態で評価**する。後日のキャンセルや返金は元の注文日の値を変更する。決済日・返金日の資金移動とは異なる。集計の期間条件は今回変更しない。

## 状態ごとの扱い

A は送料込みの注文金額。最後の列は実際の資金移動履歴を取得できた場合の考え方であり、現行の画面表示値ではない。

| 注文・決済の状態 | 注文総額 | 決済済み売上 | 実入金から実返金を控除する場合 |
| --- | ---: | ---: | --- |
| 有効・支払い待ち | A | 0 | 未回収なら 0 |
| 有効・決済エラー | A | 0 | 成功した回収を確認できなければ確定不可 |
| 有効・支払い済み | A | A | 回収 A、実返金がなければ A |
| キャンセル・支払い待ち／決済エラー | 0 | 0 | 実際の回収・返金履歴で判断 |
| キャンセル・支払い済み（返金処理前や中断） | 0 | 0 | 回収済みなら返金成功まで A を保持 |
| キャンセル・返金済み | 0 | 0 | 全額実返金なら 0。与信解放だけなら元の回収も 0 |
| キャンセル・返金エラー | 0 | 0 | 回収済みなら返金失敗では減らさない。未回収の与信解放失敗なら回収 A と見なさない |
| 有効・返金済み／返金エラー（通常の取消経路外） | A | 0 | 状態名だけで回収・返金額を推定しない |
| 未知の決済状態・有効 | A | 0 | 状態を確認するまで決済成功と見なさない |

返金エラーは期間を限定せず「対応待ち」の件数と注文一覧に引き続き表示する。キャンセルによって決済済み売上から除外されても、返金義務が消えたと解釈しない。最新注文・返金エラーの一覧に決済状態を追加し、発送状態と区別する。

## なぜ第三の金額を今は出さないか

`Order` は最新の状態・注文日時・注文合計しか保持せず、確定回収額、実返金額、回収／返金日時の履歴を保持していない。`StripePaymentGateway.refund` は `requires_capture` なら与信解放、`succeeded` なら返金リクエスト、既に `canceled` なら何もせず成功を返す。サービスはいずれも「返金済み」に更新する。また、返金リクエストが受理されたことと、その後の実返金成功は同義ではない。

このため「支払い済み＋返金済み＋返金エラー」を過去の決済額と扱うことも、「返金済み × 注文額」を実返金額と扱うことも不正確になる。決済エラーも通信失敗等による外部状態との不一致を排除できない。今回は推定値を作らず、現在の状態に基づく指標であることを説明する。

将来の拡張では、売上確定と返金のイベント（プロバイダID・金額・通貨・発生日時・成功／保留／失敗）を重複防止付きで保存し、Webhook／照合で確定する。与信解放は返金から区別する。部分返金もイベント金額で扱う。注文日基準の純額と入出金日基準の純額は別の名前で表示する。

## 影響と検証

- DB スキーマ・既存データ・決済／返金操作は変更しない。
- Repository の `orderCount` / `totalPrice` は意味を維持し、`paidOrderCount` / `paidTotalPrice` を追加する。同一の `groupBy` クエリで全体と支払い済みを得る。
- 従来「今日／今月の売上」と表示した値は「今日／今月の注文総額」に改称する。支払い待ちのデモ注文でも受注を確認できる。
- 状態別・キャンセル済み状態別・未知の状態・空集計・日本時間の日次／月次境界・後日の返金／キャンセルを回帰テストする。
- E2E は従来の未決済注文／キャンセルの確認を維持し、決済済み売上が増えないことと、各表示額が DB 集計と一致することを確認する。
